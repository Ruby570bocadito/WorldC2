## Resumen ejecutivo de las mejoras implementadas

Ronda centrada en backend por decisión del Director (la rotación de refresh tokens requería el lado cliente sincronizado, y esa fue la pieza de esta capa): la consola **persiste el refresh token rotado** que el servidor devuelve en cada `POST /api/refresh` — sin esto, el segundo refresco del cliente reusaría un token consumido y quedaría fuera. Cero cambios de vistas; un cambio quirúrgico en la capa API unificada que todas las vistas comparten.

## Detalle por mejora

### Mejora: la consola soporta la rotación de refresh tokens (acoplada al fix de z_bugs)

- **Motivación:** el server (z_bugs, esta ronda) consume el refresh token presentado y devuelve un reemplazo en `refresh_token`. El cliente existente (`doRefresh` en `web/src/utils/api.js`) solo persistía el access token nuevo: al siguiente refresco habría re-presentado el token consumido y recibido 401 — el operador sería expulsado al login en cuanto el access token caducara, exactamente el tipo de regresión silenciosa que la capa API unificada existe para evitar.
- **Cambios** (`web/src/utils/api.js`): en `doRefresh`, tras validar la respuesta, si `data.refresh_token` está presente se persiste en `bty_refresh` junto al access token y su expiración. Comentario que documenta el contrato (rotación: el presentado queda invalidado).
- **Compatibilidad:** la persistencia es condicional (`if (data.refresh_token)`) — si la consola se usa contra un servidor pre-rotación, el comportamiento es idéntico al anterior.
- **Cómo probarla:** en vivo (smoke de la ronda): login → refresh → la respuesta contiene `refresh_token` distinto del presentado → el reemplazo rota de nuevo (200) → el original reusado da 401. En consola: dejar caducar el access token (o limpiar `bty_expires`) y operar — el refresco transparente sigue funcionando cadena tras cadena (el reemplazo se reemplaza).
- **Cobertura de regreso:** `npm run build` en verde; la capa API no cambió su interfaz exportada — ninguna vista requiere edición.

## Impacto y riesgos de las mejoras

- Riesgo de regressión controlado: la persistencia es condicional y no altera la interfaz de la capa API; el build y el flujo de login/refresh existente están re-verificados.
- Con la rotación activa, el peor caso del cliente (perder el reemplazo entre la respuesta y el store) deja la sesión en estado de re-login — comportamiento idéntico al pre-rotación para un token inválido, sin lockouts.
