## Detalle por corrección

### 1. Timeout de forwarding ilimitado con `timeout_ms ≤ 0` (severidad MEDIA, agotamiento de recursos)
- **Descripción:** el POST construía `Timeout: time.Duration(whReq.Timeout) * time.Millisecond` sin acotar. Un `timeout_ms` de 0 o negativo producía una duración ≤ 0, y `http.Client.Timeout` interpreta ≤ 0 como **sin límite**: cada entrega a un endpoint muerto colgaba una goroutine indefinidamente (el forwarder lanza una por webhook por evento). Un SIEM caído + eventos regulares = acumulación gradual de goroutines bloqueadas.
- **Solución** (`internal/handlers/handlers.go`): `timeout_ms` 0 → default 5000; fuera de rango (100–60000) → 400 con mensaje JSON. El forwarder ya usa `cfg.Timeout` para el cliente — la corrección en la frontera de admisión basta.
- **Verificación:** casos `timeout_ms:50` y `timeout_ms:70000` → 400 en `TestWebhookCreateValidation`; alta sin timeout → listado muestra 5000 (smoke, paso [2]).

### 2. Filtro de eventos sin allowlist: webhook silenciosamente inerte (severidad MEDIA-BAJA, desconfiguración invisible)
- **Descripción:** `events` se almacenaba verbatim; el forwarder solo entrega si el tipo coincide (`contains`), así que `"events":["session_established"]` mal escrito (p. ej. `session_establish`) significaba un webhook que **nunca se activaba** — el operador creía tener cobertura SIEM y no la tenía. Falla cerrada, no abierta: por eso nadie la veía.
- **Solución:** allowlist `knownSIEMEvents` con los 8 tipos que el servidor emite realmente (`agent_killed`, `agent_purged`, `operator_login`, `session_disconnect`, `session_error`, `session_established`, `session_passive`, `task_result` — verificados por grep sobre los puntos de emisión). Valor desconocido → 400 listando los permitidos. La lista vacía sigue significando «reenviar todo» (semántica documentada del forwarder).
- **Verificación:** casos `["banana"]` y `["task_result","nope"]` → 400.

### 3. Caps de longitud en webhooks (severidad BAJA, higiene de entrada)
- **Descripción:** URL sin límite (una URL de megabytes entraba a la BD y al cliente HTTP), headers sin límite de número ni tamaño (map arbitrario).
- **Solución:** URL ≤ 2048; ≤ 16 headers con clave no vacía ≤ 128 y valor ≤ 1024; 400 con mensajes JSON. El guard SSRF preexistente (solo http/s absoluto) se conserva y queda como última capa tras los caps.
- **Verificación:** 4 casos de caps → 400 (incl. header vacío y valor de 1025 chars).

### 4. Caps en session notes (severidad BAJA, llenado de disco)
- **Descripción:** `POST /api/notes` solo comprobaba no-vacío: un cuerpo de cualquier tamaño se persistía para siempre en `session_notes` (sin TTL ni purga).
- **Solución:** `session_id` ≤ 128 chars, `content` ≤ 10000 chars → 400 con mensaje JSON. La nota válida sigue entrando igual (el id de sesión no se valida contra la tabla por diseño del endpoint).
- **Verificación:** `TestNotesValidation` (ambos caps + nota válida → 200); smoke paso [6]: cuerpo de 10001 → 400.
