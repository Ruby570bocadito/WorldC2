## Resumen ejecutivo de bugs/vulnerabilidades corregidos

**1 cadena de vulnerabilidad con 3 defectos apilados**, descubierta al auditar el ciclo de vida de las cuentas de operador (la única superficie no auditada en profundidad): **borrar un operador no le quitaba el acceso**. (1) `RevokeUser` se llamaba con el segmento crudo de la URL (id numérico) mientras el mapa de revocación está indexado por username (el subject del JWT) — la revocación en memoria nunca revocó a un operador real; (2) el mapa de revocación es volátil (muere con el proceso) pero la clave de firma JWT se recarga persistida — tras un reinicio, los tokens del operador borrado volvían a validar durante lo que quedaba de su TTL de 12h; (3) `DeleteOperator` con id inexistente era un no-op que respondía `{"status":"deleted"}` — falso éxito destructivo. La corrección es en profundidad: resolver-antes-de-borrar (404/400 explícitos), revocar por el username resuelto, y un **existence check en el authMiddleware** que rechaza cualquier token cuyo username ya no exista en la tabla de operadores — con o sin reinicio, cubriendo la clase entera de "tokens de cuentas muertas". **Verificación:** `go test -race` 8 paquetes en verde con 4 tests nuevos de integración; smoke en vivo con ciclo completo y **reinicio real del servidor** (token del operador borrado sigue en 401).

## Detalle por corrección

### 1. Borrar un operador no le revocaba el acceso (N1 del Director — severidad MEDIA)

**Anatomía del hallazgo** (cada defecto por separado parecía benigno; juntos anulan la función):

- **Defecto A — keying incorrecto:** `handleOperatorDelete` hacía `RevokeUser(req.URL.Path[len("/api/operators/"):])`. La consola pasa `op.id` (numérico — `ListOperators` devuelve el `ID int` de la fila), así que se revocaba el username `"2"`. Los JWT llevan `sub=<username>` y `validate()` consulta `revokedBefore[payload.Sub]` — **el mapa correcto nunca era consultado con la clave correcta**. Consecuencia: la revocación in-memory de la ronda 1 era, en producción, un no-op silencioso.
- **Defecto B — volatilidad de la revocación:** el mapa vive en el `TokenManager`; el signing key se persiste en `server_secrets` (el comentario del propio handler lo admitía: "the signing key is persisted... without an explicit revocation the deleted operator would keep API access until token expiry" — pero la revocación explícita se perdía con el proceso). Escenario: borrar operador → reinicio (deploy, crash, host reboot) → sus tokens vuelven a validar.
- **Defecto C — falso éxito:** `DeleteOperator` ejecuta `DELETE ... WHERE id=?` sin reportar filas afectadas; un id mal tecleado (o el test usando username en vez de id) respondía 200 igualmente. Mismo anti-patrón que la ronda 6 corrigió en `?purge=true`.

**Solución** (tres capas, cada una con su justificación):

- `internal/db/database.go` — nuevo `GetOperatorByID(id int) (*OperatorRecord, error)`: resuelve la cuenta por su PK numérica. El handler ahora **resuelve antes de borrar**: id malformado → 400, id desconocido → 404; y de la fila resuelta obtiene el **username real** para la revocación.
- `internal/handlers/handlers.go` — `handleOperatorDelete`: `strconv.Atoi` sobre el segmento → `GetOperatorByID` → `DeleteOperator` → `RevokeUser(op.Username)` → respuesta `{"status":"deleted","username":...}` y audit log con ambos identificadores. La revocación in-memory vuelve a funcionar (inmediata, sin esperar al siguiente arranque).
- `internal/handlers/router.go` — `authMiddleware`: tras `ValidateToken`, **`OperatorExists(username)`** (nuevo, en la capa BD): si el username ya no existe → `auth_failed` + 401. Coste: un SELECT indexado sobre una tabla de pocas filas por petición — irrelevante frente al handler real. Esta capa es la garantía permanente: no hay estado que perder en un reinicio, y cubre cualquier otro camino por el que una cuenta deje de existir.
- `internal/db/database.go` — `OperatorExists`: `SELECT 1 ... WHERE username=?` con distinción limpia de `sql.ErrNoRows`.

**Tests** (`internal/handlers/authz_test.go` — stack de integración completo: BD real + `c2.New` + `NewRouter` + mux, sobre temp dir):

- `TestDeletedOperatorTokenRejectedImmediately`: login de alice → 200 en `/api/sessions` → DELETE del id real de alice → **401 inmediato** para su token; y borrado de un id inexistente con el token de un segundo admin (bob) → **404**.
- `TestDeletedOperatorTokenRejectedAfterRestart`: tras borrar a alice, una **segunda instancia Server/Router sobre la misma BD** (recarga el signing key persistido, mapa de revocación vacío — simulación exacta de un reinicio) → su token sigue en **401**. Este test es el que falló con el código viejo y demostró el Defecto A por el camino (el keying erróneo dejaba a alice viva).
- El keying correcto queda fijado por la respuesta: `{"status":"deleted","username":"bob"}` — el handler declara a quién revocó.

**Verificación (en vivo):** smoke con binario fresco (md5 registrado): admin crea bob → bob loguea → admin borra a bob (id 2) → token de bob **401** → re-borrado del id **404** → id `"abc"` **400**. Luego carol (viewer) creada y borrada, **reinicio real del proceso**, token de carol → **401**. La cadena completa está cerrada en producción, no solo en tests.

**Nota de trazabilidad operativa** (registrada por z_pulimiento): cualquier despliegue que haya borrado operadores antes de este fix asumiendo pérdida de acceso debería revisar sesiones/tokens emitidos — los access tokens de 12h emitidos antes del borrado habrán expirado ya, pero es la comprobación honesta.
